# 內容更新紀錄

本紀錄用於追蹤網站知識內容的修改。每次涉及法規、金融、行情、民泊或 AI 知識的重要更新，都應新增一筆紀錄。

## 2026-09-15｜圖紙解析架構升級：AI 結構化輸出（消除 2900 行 Regex 脆弱層）

為從根本解決「每張新圖紙就因為版面、分隔符或漢字異體字差異而爆出新 bug」的脆弱性，將原本由手工 regex 執行的**切句、分類、翻譯**三項工作全面移交 Gemini 結構化輸出 schema 處理，既有 regex 降級為向下相容 fallback。

- **Phase 1: 交通動線結構化**（`transitLegs`）：
  - Gemini Schema 新增 `transitLegs` 物件陣列：`lineName`（鐵道路線名）、`stationName`（站名）、`walkMin`（步行分鐘）、`busMin`（巴士車程）、`busStop`（巴士站名）。
  - `reconcileTransitAccess()` 優先採用 AI 結構化動線，自動消除線名站名黏連（如「総武本線馬喰町駅」）與多線去重錯位問題。
- **Phase 2: 租賃條件條目結構化與直譯**（`rentalConditionItems`）：
  - Gemini Schema 新增 `rentalConditionItems` 陣列：`category`（`lease`/`moveIn`/`pet`/`guarantee`/`fees`/`moveOut`/`optional`）、`ja`（原文）、`zh`（繁體中文翻譯）。
  - AI 直接按圖面排版理解條目邊界，不再受制於 `split(/[。\n]+/)` 或特定符號（`■◆●▲`），且能精準翻譯帶有前提條件的子句。
  - `rentalConditionGroups()` 優先採用結構化條目組裝前端分組，無結構化資料時自動退回既有 regex 管線。
- **Phase 3: 備考特約結構化與直譯**（`specialNoteItems`）：
  - Gemini Schema 新增 `specialNoteItems` 陣列：`category`（契約特約、費用約定、生活規範、使用限制、入住條件等）、`title`、`zh`、`ja`、`tone`（`amber`/`emerald`/`blue`/`neutral`）。
  - `parseAndExplainSpecialNotes()` 優先採用結構化條目生成卡片，無結構化資料時自動退回規則字典比對。
- **向下相容與防護**：
  - 網頁端 `ListingHealthCheck`、`RentalConditionSummary`、`OtherConditionNotes` 與 PDF 端 `RentalSections`、`SpecialNotesCard` 全面支援雙軌輸入。
  - 既有 25 支測試腳本與全量 golden fixture 100% 通過。

## 2026-09-15｜アデニウム東神田端到端測試：路線名、退租特約、Overpass 超時

- **路線名消失**（`transitParser.ts`）：圖紙寫「総武本線馬喰町駅 徒歩3分」——
  線名與站名無分隔符，原本按空白或「／」切分只會切出一段，整串被當成站名，
  `lineName` 留空。前端「最近車站」卡片只剩站名+分鐘。新增 `splitGluedLineAndStation()`
  用路線名後綴（線/ライン/エクスプレス/モノレール/新交通/地下鉄）當切點，取最後一個
  避免「都営新宿線」被誤切。12 種邊界案例全部正確，且不會影響無路線名的純站名寫法。
- **退租特約全部丟失**（`rentalConditionDisplay.ts`）：リブマックス 系圖紙用「■」
  串連二十多條特約，切句器只認「。\n」，整串變成一句、翻譯規則全部配不到——
  退租結算手續費 5,500 円、鍍膜清潔費 55,000 円、短期解約違約金等對租客有實質
  金額影響的費用條件，前端完全不顯示。修正切句器支持 `■◆●▲☆★` 項目符號，
  並為このタイプ圖紙常見的 18 種日文特約逐條添加中文翻譯規則。
- **周邊設施「資料待確認」**（`listingLocation.ts`）：Overpass 伺服器端 `[timeout:8]`
  與客戶端 `AbortSignal.timeout(8000)` 設成同值，等於把網路傳輸與排隊時間預算設為零。
  實測東京都心（千代田区東神田）四個端點回傳 658 筆、耗時 6.0～9.4 秒——資料存在
  但臨界超時。伺服器預算放寬至 25 秒、客戶端 30 秒。

## 2026-09-15｜圖紙分析改用 medium 解析度，並修復 controller-flows 測試

- `analyze-listing` 的三處 Gemini 呼叫統一以 `toInlinePart()` 送出，指定
  `mediaResolution: medium`。官方對 PDF 的建議值即為 medium，實測也支持：
  以レオパレス図面（2200px JPEG 與原始 PDF）各跑 5 次，預設／medium／high 在礼金、
  家賃、専有面積、鍵交換費、退去清掃費、保証委託料、火災保険、住所、築年數等欄位
  **全部 5/5 相同**，但 medium 的 prompt token 比預設少約 43～47%（1307→747、1197→637）。
  結論：預設值對單頁図面等同 high，多付的 token 換不到準確度；小格子判讀的瓶頸
  是提示詞有沒有講清楚要去哪裡找值，不是解析度。
- 同一組實測也驗證了前一筆「無單位數字＝月數」規則的實際價值：舊提示詞在預設與 high
  解析度下都能看到那個數字，但輸出的是裸 `1`，而 `parseMonthsOrYen("1", 45000)` 會回
  `null`（初期費用漏算一個月租金）；補上規則後輸出 `1ヶ月`，換算為 45,000 円。
  亦即該欄位先前的失準來自單位缺失，與模型視力無關。
- 修復月數單位全面失配：日文寫「一個月」的字形各家不同、碼位卻互不相等——
  ヶ(U+30F6)、ヵ(U+30F5)、ケ(U+30B1)、カ(U+30AB)、か(U+304B)、ｹ(U+FF79)。原本 6 個檔案
  共 19 處月數比對只列了 ヶ／ヵ／カ／個，於是 `parseMonthsOrYen("1ケ月", 45000)` 回
  `null`，礼金整整一個月租金沒被算進初期費用；敷引月數、契約條件翻譯、備考特約比對
  也同樣整筆失效。改採入口正規化：新增 `normalizeMonthUnit()` 把 `[ケヶヵカかｹ]月`
  統一成 `ヶ月`，在 `toHalfWidth`、`leaseTermValue`、`rentalConditionGroups`、
  `parseAndExplainSpecialNotes`、`reconcileRentalListingText` 等各管線入口套用，
  下游只需認得一種寫法——比在十餘處規則運算式各自補字元更不容易漏，日後新增程式碼
  也不會再犯同樣的錯。規則限定「後面接月」才改寫，「ケーキ」「赤坂」「明かり」不受影響。
- 平假名「か月」是補測「アデニウム東神田」図面時才發現的第六種寫法：該圖備考欄寫著
  「法人で保証会社加入無しの場合、敷金1か月」，實測 `parseMonthsOrYen("1か月", 219000)`
  回 `null`。它同時也是日本官方公文與報紙的標準寫法，漏接的風險不低於「ケ月」。
  一併補上第 7 個未正規化的入口 `rentalListingReconciliation.ts`——該檔另有兩處寫死
  `ヵ月` 的比對，上游統一後會配不到，已改為 `ヶ月`（與 `rentalConditionDisplay.ts`
  先前的修法一致，再次印證「每處各自列舉字元」這個模式的脆弱）。
- 修復 `test:controller-flows`：PDF 匯出 payload 新增 `safety` 欄位後，歷史 fixture
  比對失敗。既有程式碼已針對 `state` 補上 `prefectureSafety: null`，但 `pending`
  未做對應處理。新增 `withoutSafety()`，僅在值為 `null` 時移除該鍵——有實際治安
  資料時仍應能看出差異，不可靜默吃掉。

## 2026-09-15｜圖紙解析：修正版面還原，並讓圖片上傳也具備欄位對位

レオパレス 版型圖紙（`29267_20260915.pdf`）讀不出「礼金 1」與完整地址，追查後發現三個獨立成因，
其中最關鍵的一項同時影響 PDF 與圖片兩種上傳方式。

- **礼金讀不出的主因是提示詞寫死版型假設**（`api/analyze-listing.ts`）。
  `verifyLeaseCharges` 原本要求「值就在標籤正右方」，而該圖紙是「標題列在上、值在下」的直向表格，
  這條規則反而把模型導向錯誤位置。改為兩種版型都嘗試，右方找不到時務必再找正下方對齊的值。
  這一層 PDF 與圖片共用，是本次唯一的通用修正。
- **無單位數字的解讀規則**：日本賃貸図面常把「ヶ月」印在表頭或省略，格子僅留「1」。
  提示詞補上「單獨數字視為月數」，並限定有千分位逗號或四位數以上者仍當金額，避免把 45,000 誤判成月數。
  主抽取與二次確認兩處同步更新，避免兩層判斷不一致。
- **地址黏連**（`src/lib/listing/browser/pdfRendering.ts`）：該圖紙每個字都是獨立文字項，
  原本一律以全形空格連接，導致「■32型液晶テレビ」與「住所：」之間沒有邊界。改為依實際 x 間距決定分隔。
- **列合併滾雪球**：原本 `row.y = (row.y + item.y) / 2` 會讓列中心隨新項目漂移，
  逐步把後續各列吸進同一列（實測 92 個文字項跨 13pt 併成一列）。改用固定錨點，容忍度由中位字高推導。
- **欄位垂直對位**：該圖紙的表格標題幾乎都是背景圖片，文字層只有「礼金」二字，
  且標題（y=174.5）與值（y=135）相隔 39pt，任何列合併門檻都併不到一起，唯一線索是 x 座標對齊。
  新增對位掃描，結果以獨立區塊附在版面文字末尾。橫向表格因標題右方緊鄰即有值，不會產生錯誤對位。
- **圖片上傳的對位資訊**：`layoutText` 來自 PDF 文字層，圖片路徑一直是空字串，等於少掉整層保護。
  新增 `transcribeImageLayout()`，以一次窄呼叫轉寫費用表作為對位提示。
  轉寫結果**刻意不併入 `layoutText`**：後者在 `reconcileRentalListingText` 與交通動線漏抄校驗中
  被當成「不受 AI 判讀影響的基準」，灌入 AI 轉寫內容等於拿 AI 校驗 AI，幻覺會被當事實回補。
  因此它只以提示參與抽取，且語氣弱於文字層提示（與圖片牴觸時以圖片為準）。
- 新增 `npm run test:pdf-layout`（`scripts/test-pdf-layout-text.ts`），涵蓋欄位邊界、滾雪球防護、
  垂直對位與橫向表格安全性五個案例。已用缺陷注入確認三項修正各自都能被測出回歸。
- `scripts/test-listing-upload.ts` 的 PDF fixture 補上 `width` 與字高（真實 pdf.js 必帶），
  期望值隨新的間距分隔更新。

注意：分隔符變更不影響既有欄位比對——`rentalListingReconciliation.ts` 的 `compactText()`
會清除所有空白；唯一依賴空白的 `buildingName` 用的是半形 `[ \t]{10,}`，不受全形分隔影響。

### 附：為何不引入 OCR 套件（已實測評估，勿重複嘗試）

此版型的表格標題多為背景圖片，直覺上「裝個 OCR 就能讀」。實際以 tesseract.js（jpn）
對同一份圖紙測過四種配置，與現行方案比較 9 個關鍵欄位：

| 方案 | 正確 | 耗時 | 體積 |
| --- | --- | --- | --- |
| 文字層＋垂直對位（現行） | 9/9 | ~50ms | 0 |
| tesseract 200dpi 整頁 | 5/9 | 7.6s | ~50MB |
| tesseract 400dpi 整頁 | 2/9 | 10.9s | ~50MB |
| tesseract 裁切費用表 6x | 4/9 | 0.3s | ~50MB |

- 「礼金」二字在所有配置下**沒有一次辨識正確**（讀成「礼信」「れ人」），平均信心度僅 46～53。
- 金額誤讀最危險：`45,000` 被讀成 `78.000`，會讓初期費用試算出錯且下游無法察覺。
- 提高解析度反而更差（400dpi 僅 2/9），非調參可解。
- OCR 唯一的優勢是能讀到背景圖裡的標題列，但 Gemini 本身就看得到圖像且日文辨識遠勝 tesseract；
  為此付出 50MB 依賴與數秒延遲並不划算，Vercel serverless 的冷啟動與記憶體也難以負擔。
- PaddleOCR／manga-ocr 日文準確度較佳，但屬 Python 模型（數百 MB）須另架推論服務；
  Google Cloud Vision 則是在已付費使用 Gemini 的情況下重複付費購買更弱的能力。

若未來圖紙解析成為核心業務且量大到值得自架，再評估 PaddleOCR 加版面分析。

- 租賃圖紙行情由 210 個精選地區擴為全 47 都道府縣、1,192 個有公開租金值的市區町村、4,785 個格局值；地圖與車站推薦維持原精選範圍。
- 修正空白車站可能讓無法辨識的地址誤配到第一個行政區，以及沖繩、姬路、濱松等新舊字形的全國地址比對。
- 國交省成交快照由原 210 地區擴為全 47 都道府縣、506 個有合格樣本的市區町村、1,389 個市區町村／格局分桶；地址解析同步全國化。
- 新增 At Home 中古公寓公開刊登靜態快照：498 個市區町村、1,689 個有效格局值；SUUMO 與 HOME'S 以全國交叉核對入口呈現，不混算不同統計口徑。
- REINS 開價備援擴到首都、中部、近畿三圈；西日本公開摘要只有成約價時保持缺值。
- 新增東日本 REINS 2026-07 首都圈中古公寓成約／新規登錄㎡單價常數，買賣圖紙同時顯示成約行情與市場典型開價。
- 明示 REINS 是兩組市場物件的平均差距，不把 28.6% 的反向差距冒充個案必然議價幅度。
- MLIT 快照新增成交㎡單價、代表面積、建築年覆蓋、構造計數與至少 5 筆才採用的屋齡分層；全國版 953／1,389 個粗分桶已有合格屋齡子分桶。
- 估價改為優先使用「同區 × 同房型 × 同屋齡帶㎡單價」，不足時回退同區同房型㎡單價；避免同時再加一次手估屋齡係數。
- 補上非塔樓最上階 +6% 的獨立處理。
- 複核 At Home、SUUMO、LIFULL HOME'S 公開租金行情入口與統計口徑；三者保留分來源比較，不直接混算。
- 以三軒茶屋、淺草、錦糸町、市川行德 4 份真實販売図面完成端到端回歸；修正可選停車位誤算固定月費、修繕積立金改定額未優先、全面翻新未觸發係數等問題。
- 同房型缺少目標屋齡帶時，新增同區跨房型的屋齡㎡單價備援，並在畫面標明備援口徑與實際分層樣本數。

主要來源：東日本 REINS 月例 Market Watch、國土交通省不動產資訊資料庫 XIT001、At Home／SUUMO／LIFULL HOME'S 公開租金行情頁。

## 2026-09-01｜國交省買賣成交快照啟用

- 啟用國交省不動產資訊資料庫 XIT001 交易資料靜態快照。
- 最新季度為 2026-Q1，共匯入 761 組資料；663 組採最新四季，98 組因近期樣本不足採最新八季，網站 210 個地區均至少涵蓋一種格局。
- 成交中位數改為最新四季優先；四季不足 5 筆時擴大至最新八季，仍不足才回退租金收益率模型，避免舊年度資料稀釋近期行情。
- 每組至少 5 筆交易才採用官方中位數；不足時繼續使用租金收益率模型，避免把小樣本當成行情。
- 更新來源狀態、維護文件與測試，使買房地圖及試算器優先使用相同的成交資料。

## 2026-08-31｜行情更新流程與成交 API 接口

- 建立 At Home、SUUMO、LIFULL HOME'S 與國交省不動產資訊資料庫的來源／更新矩陣。
- At Home 公開頁更新工具按季建立靜態快照，保留缺值與差異檢查。
- 快照保存 13 種原始格局，主畫面以中位數整理為 5 個相近格局群組；`4LDK以上` 不混入 3LDK 群組，避免大型豪宅拉高行情。
- 租金地圖、租屋試算與行情卡新增 `3LDK+`；實測 210／210 個地區有 3LDK 資料。
- 租金快照改為每季檢查、超過 100 天警示。
- 建立國交省 XIT001 買賣交易快照產生器；API 核准前保留空快照，不假造實際成交資料。
- 買房試算器會優先使用合格的國交省行政區／間取り交易中位數；沒有資料時明示沿用租金收益率模型。
- 買房地圖與試算器改用同一個估價函式，避免兩邊的收益率假設不一致。
- 加入國交省 API 規約指定 credit，僅在正式使用該快照時顯示。
- 新增 `docs/MARKET_MAP_BLUEPRINT.md`，記錄現在、累積四季後及取得國交省 API 後的實作邊界。

主要來源：At Home 公開相場頁、SUUMO／LIFULL HOME'S 公開相場頁、國土交通省 XIT001 API 說明與 API 利用規約。
