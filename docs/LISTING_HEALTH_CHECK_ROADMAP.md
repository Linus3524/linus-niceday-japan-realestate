# 物件圖紙健檢：呈現內容藍圖

## 目標

使用者上傳仲介提供的物件概要書／図面，回答一個既有功能回答不了的問題——**「我手上這間，到底值不值？」**

站內既有的租屋需求分析回答的是相反方向的問題（「我該往哪找」），兩者刻意分開呈現，不混在同一條步驟流程裡。

這份文件整理**分析結果卡片上想呈現哪些資料**，以及每一項的現況與前置條件。

---

## 為什麼是「上傳圖紙」而不是「貼物件網址」

原本考慮讓使用者貼 SUUMO／At Home／LIFULL HOME'S 的物件網址自動抓取，**已明確排除**：

- 這類平台的使用條款通常禁止自動化存取，對持牌仲介的自有品牌網站是不必要的法律與商譽風險。
- 頁面結構不受我們控制，改版即失效，維護成本長期偏高。

改為使用者自行上傳圖紙，完全落在「使用者提供自己手上的資料」的正常範圍內，不涉及存取第三方網站。

**額外的關鍵好處**：図面上有**具體地址**。這正是解鎖下方第二階段所有功能的鑰匙（詳見「為什麼周邊機能一定要等到這個階段」）。

---

## 第一階段：已完成

### 1. 圖紙欄位抓取

Gemini vision 讀出以下欄位，原文照抄不翻譯、不換算：

| 欄位 | 說明 |
| --- | --- |
| `station` / `walkTime` | 車站與各自的徒步分鐘數，多站以逗號分隔且順序對應 |
| `layout` | 間取り（1LDK、2DK…） |
| `rent` / `managementFee` | 賃料／家賃、管理費／共益費 |
| `keyMoney` / `deposit` | 礼金、敷金（「1ヶ月」與「10万円」兩種寫法都要能處理） |
| `age` / `floor` | 築年數、所在階 |
| `address` | 所在地 |

### 2. 租金合理度（核心）

**租金＋管理費**與該地區、該房型的行情區間比對，複用既有的 `resolveSearchScope`／`estimateRequestedRent`，不另外造一套行情邏輯。

結論沿用站內既有的狀態詞彙（符合／部分符合／需調整／難度高／待確認），視覺與需求分析卡片同一套配色，使用者不用學新的視覺語言：

- **低於行情低端** → 提示留意是否有圖紙上未列出的成本，或屋齡、樓層、環境上的取捨（價格偏低不必然是壞事，但值得問清楚）
- **落在區間內** → 依接近中位的程度分級
- **高於行情高端** → 提示向仲介確認加價的具體原因（新裝潢、高樓層、免費網路、自動鎖…），而不是單純接受「比較貴」

### 3. 初期費用提示

敷金＋礼金合計換算成月數，超過 3 個月才跳提示，避免每次都跳、變成使用者自動略過的雜訊。目前刻意只做簡單門檻，不做精細模型。

## 第二階段：已完成

以下功能已接在第一階段分析結果下方。位置資料取得失敗時採降級呈現，不會讓租金合理度分析一起失敗。

### 前置條件：地址 → 座標（geocoding）

使用國土地理院地址搜尋將圖紙地址轉成座標，並在伺服器端做暫存快取。若圖紙沒有地址或定位失敗，畫面會保留第一階段結果並說明無法提供位置資訊。

### 4. 實際步行到車站時間（三種速率）

圖紙上寫的「徒歩8分」是日本業界慣例的換算值（**80 公尺＝1 分鐘**，且不計紅綠燈、坡道、天橋），與真實步行時間經常有落差。

想呈現的是依實際路徑距離換算的三種速率，讓使用者對照自己的狀況：

| 速率 | 對應情境 |
| --- | --- |
| 快走 | 趕電車、單身通勤族 |
| 一般 | 日常往返 |
| 慢走 | 推嬰兒車、拉行李、長輩、雨天 |

**同時也是對圖紙數字的驗證**——圖紙寫 8 分但實際路徑要走 12 分，這件事本身就值得標示出來。

已實作：以 OpenStreetMap 步行路網取得物件到各圖紙車站的實際路徑距離，再分別用快走、一般、慢走／行李三種速度換算。一般速度比圖紙標示多 3 分鐘以上時以提示色標記。

### 5. 周邊生活機能（含國交省設施距離）

超商、超市、藥妝、醫療、學校、公園等，**以物件座標為圓心**列出距離。

#### 為什麼一定要等到這個階段

這一點先前已經討論並否決過一次：原本想在「租屋需求分析的推薦車站」上加周邊機能，但那裡只到**車站層級**（`RentRecommendation.station` 只是站名字串，沒有座標），問題是：

- **對新宿這種轉運站毫無鑑別度**——光新宿站周邊就有上百間超商，列出來完全無法幫使用者做決定。
- **對郊區小站又缺乏具體地址**，同樣答不出「我要看的**這間房子**附近有什麼」。

換句話說，周邊機能這件事**只有在拿到單一物件的精確座標時才有意義**，而這正是圖紙上的地址能提供的。這也是為什麼它被放在圖紙健檢底下，而不是需求分析底下。

已實作：列出 1.2 公里內各類別最近 3 筆。超商、超市、藥妝／藥局與公園使用 OpenStreetMap；學校與醫療機構使用國土交通省不動產資訊資料庫 API，並在畫面顯示來源、必要 credit 與資料可能缺漏的說明。

### 6. 通勤目的地距離

使用者輸入自己的公司／學校地址，計算到該物件的實際通勤時間與轉乘次數。

這是「合不合理」之外的另一個維度——**對這個使用者本人來說方不方便**。租金再合理，通勤 90 分鐘也不會是好選擇。

已實作：使用者可輸入公司／學校完整地址，或直接輸入最近車站。地址會先定位並尋找最近車站，再合併「物件到車站步行＋平日班表電車時間＋目的站到目的地步行」，顯示總時間與轉乘次數。

### 第二階段技術路徑

- `POST /api/listing-location` 的 `context` 模式：地址定位、車站步行路徑、周邊設施。
- `POST /api/listing-location` 的 `commute` 模式：目的地定位與通勤時間。
- 地址定位：國土地理院地址搜尋。
- 步行路徑與民間生活設施：OpenStreetMap 資料與 FOSSGIS routing 服務；每秒最多一次路由請求。
- 學校、醫療機構：國土交通省不動產資訊資料庫 `XKT006`／`XKT010`。
- 電車路線：複用站內既有 GTFS 路線計算與驗證邏輯。

## 明確不做

| 項目 | 原因 |
| --- | --- |
| 物件網址自動抓取（SUUMO／At Home／HOMES） | 法律與商譽風險，已排除 |
| 買賣（SALE）模式的圖紙辨識 | 本輪維持租賃側，與原始需求範圍一致 |
| 4LDK 以上的行情比對 | 行情資料本身就沒收錄這個級距，硬塞進 3LDK+ 只會失真，誠實顯示「查無此房型行情」 |

## 隱私

上傳的圖紙可能包含地址、聯絡電話等資訊。伺服器端**不落地儲存**上傳圖片，僅在記憶體中處理、回傳結果後即丟棄，與站內 AI 顧問「輸入內容僅用於產生本次回答」的立場一致。上傳區塊已標示這一點。

---

## 技術限制備忘

- **Vercel request body 硬上限 4.5MB，不可調**。base64 會讓體積膨脹約 1.37 倍，因此上傳合計上限設為 3MB。
- 為此前端在上傳前會自動縮圖（長邊 2000px、JPEG quality 0.8、依 EXIF 轉正）。Gemini vision 本來就會自行降採樣，縮圖不影響辨識結果。實測 40MB 的圖可壓到約 0.96MB。
- 獨立於 `/api/rent-analysis` 的限流額度（5 分鐘 3 次），避免兩個功能互相排擠。
